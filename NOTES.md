Принятые допущения

Тестовые данные создаются автоматически при первом запуске приложения. Если коллекция сотрудников уже содержит данные, повторное заполнение базы не выполняется.
Для тестовых данных используется фиксированный набор сотрудников, проектов, ставок, закрытого периода и записей табеля.
Ставка сотрудника определяется по последней записи Rate, дата начала которой не позже даты записи табеля.
Закрытый период определяется по сочетанию года и месяца.
Запись табеля не может содержать более 24 часов. При суммарной загрузке сотрудника более 12 часов запись помечается как сверхурочная.
Для защиты от одновременного изменения одной записи используется поле Version.
Расчёт стоимости записи выполняется как количество часов, умноженное на ставку сотрудника, с округлением результата до двух знаков после запятой.
Frontend и backend являются отдельными частями приложения и взаимодействуют через HTTP API.
Объяснение выбранных решений

Для работы с MongoDB создан отдельный MongoDbContext, через который сервисы получают доступ к базе данных. Инициализация MongoDB, создание индексов и загрузка тестовых данных вынесены в отдельные классы MongoDbInitializer и MongoDbIndexes.
Бизнес-логика работы с табелем сосредоточена в одном файле TimeEntryService. В нём выполняются проверки сотрудника, проекта, даты проекта, закрытого периода, ставки и количества часов. Это позволяет не переносить основные бизнес-правила во frontend и выполнять их на стороне backend.

Для ошибок бизнес-логики используется BusinessException с кодом ошибки. Отдельный middleware преобразует такие исключения в HTTP-ответ, благодаря чему frontend получает единообразную информацию об ошибках.
Для получения табеля реализована фильтрация по году, месяцу, сотруднику и проекту, а также пагинация. Расчёт стоимости записи выполняется на backend, поэтому frontend получает уже рассчитанное значение.
Для формирования отчёта по проектам используется отдельный сервис. В отчёте рассчитываются количество часов, стоимость работ, процент использования бюджета, а также признаки превышения бюджета и риска.

Обоснование индексов

Индексы создаются автоматически при запуске приложения в классе MongoDbIndexes.
Для коллекции time_entries созданы три индекса. Индекс по Date используется при выборке записей за определённый период. Составной индекс EmployeeId + Date предназначен для фильтрации записей конкретного сотрудника по дате. Составной индекс ProjectId + Date используется для фильтрации записей конкретного проекта по дате.
Для коллекции projects создан уникальный индекс по ProjectCode, чтобы два проекта не могли иметь одинаковый код.
Для коллекции closed_periods создан уникальный составной индекс Year + Month. Он соответствует структуре закрытого периода и не позволяет создать несколько записей для одного и того же месяца.
Индексы выбраны исходя из фактически используемых в приложении фильтров и ограничений целостности данных.

Что осознанно не доделано

Полноценные интеграционные тесты API не реализованы. В проекте добавлены unit-тесты для отдельных бизнес-правил и ключевых сценариев сервиса.
Не реализована полноценная тестовая инфраструктура с отдельной MongoDB для автоматического запуска тестов. Часть тестов, работающих с MongoDB, использует локальную тестовую базу.
Не добавлена отдельная конфигурация для разных окружений с автоматическим выбором параметров подключения к тестовой и рабочей базе.
Не реализована авторизация и разграничение прав доступа, так как это не требовалось в рамках тестового задания.
Не добавлена полноценная обработка конкурентных изменений на уровне всех возможных операций с данными. Для основных операций изменения и удаления используется Version.
Не проводилась отдельная оптимизация производительности frontend и backend сверх необходимых для задания решений.

Что сделал бы иначе, будь времени вдвое больше

В первую очередь добавил бы полноценные интеграционные тесты API, включая создание, изменение, удаление и получение записей табеля, работу с закрытыми периодами и формирование отчётов.
Для тестов организовал бы отдельную MongoDB, например через Docker Compose, чтобы тесты могли запускаться в чистом окружении и не зависели от состояния локальной базы разработчика.
Также пересмотрел бы структуру TimeEntryService и разделил часть бизнес-логики на более небольшие компоненты. Это упростило бы тестирование отдельных сценариев и сделало сервис менее объёмным.
Отдельно проверил бы запросы к MongoDB и планы выполнения запросов для основных операций, чтобы подтвердить эффективность выбранных индексов на большем объёме данных.
На frontend уделил бы больше внимания разделению компонентов, обработке состояний загрузки и ошибок и визуальному оформлению интерфейса.
При дальнейшем развитии проекта также добавил бы конфигурацию окружений, более подробное логирование и автоматический запуск тестов в CI.
