1. Найденные проблемы
1.1. TimesheetReportHandler.cs
Критические:
    1. Загрузка всех записей time_entries в память

    Фрагмент:
    .Find(FilterDefinition<TimeEntry>.Empty)
    .ToListAsync();

    Все записи из коллекции загружаются в память приложения, после чего фильтруются по году и месяцу в C#.

    Чем грозит: при нескольких миллионах записей значительно возрастает потребление памяти и время выполнения запроса. В худшем случае приложение может получить OutOfMemoryException. Такой подход также не соответствует требованию задания об агрегации на стороне MongoDB.

    Как исправить: перенести фильтрацию и группировку в MongoDB через Aggregate(). Фильтровать записи по диапазону дат непосредственно в базе.

    2. N+1 запросов к коллекции employees

    Фрагмент:
    var employee = _db.GetCollection<Employee>("employees")
    .Find(e => e.Id == entry.EmployeeId)
    .FirstOrDefaultAsync().Result;

    Для каждой записи табеля выполняется отдельный запрос к employees.

    Чем грозит: количество запросов к MongoDB растёт вместе с количеством записей. При большом объёме данных это существенно увеличивает время формирования отчёта и нагрузку на БД.

    Как исправить: получать сотрудников одним запросом или использовать $lookup в MongoDB aggregation.

    3. N+1 запросов к коллекции projects

    Фрагмент:
    var project = await _db.GetCollection<Project>("projects")
    .Find(p => p.Id == entry.ProjectId)
    .FirstOrDefaultAsync();

    Запрос выполняется отдельно для каждого нового проекта.

    Чем грозит: при большом количестве проектов увеличивается количество обращений к БД и время формирования отчёта.

    Как исправить: получать данные проектов в рамках одной агрегации через $lookup либо загрузить необходимые проекты одним запросом.

    4. Неправильный выбор часовой ставки

    Фрагмент:
    var rate = employee.Rates.FirstOrDefault().Value;

    Выбирается первая ставка сотрудника независимо от даты записи.

    Чем грозит: стоимость исторических записей может рассчитываться неверно после изменения ставки. Например, для записи после 01.03.2026 может использоваться ставка, действовавшая до этой даты.

    Как исправить: выбирать последнюю ставку, для которой Rate.From <= entry.Date.

Высокий приоритет:
    5. Синхронное ожидание асинхронного запроса

    Фрагмент:
    FirstOrDefaultAsync().Result;

    Асинхронная операция блокируется синхронным ожиданием.

    Чем грозит: блокировка потока и снижение пропускной способности приложения при высокой нагрузке.

    Как исправить: использовать await и передавать CancellationToken.

    6. Использование double для денежных значений

    Фрагменты:
    public double Amount { get; set; }
    public double Budget { get; set; }
    public double Value { get; set; }

    double используется для стоимости, бюджета и ставки.

    Чем грозит: двоичное представление double может приводить к ошибкам точности при денежных расчётах.

    Как исправить: использовать decimal.

    7. Возможный NullReferenceException при отсутствии сотрудника

    Фрагмент:
    var rate = employee.Rates.FirstOrDefault().Value;

    Если сотрудник не найден, employee будет null.

    Чем грозит: необработанная ошибка приведёт к HTTP 500.

    Как исправить: явно проверять наличие сотрудника и корректно обрабатывать ошибочную ссылку на сотрудника.

    8. Возможный NullReferenceException при отсутствии проекта

    Фрагмент:
    ProjectId = project.Id,
    ProjectName = project.Name,

    Если проект не найден, project будет null.

    Чем грозит: отчёт завершится исключением вместо контролируемой обработки ошибки.

    Как исправить: проверять результат поиска проекта и явно обрабатывать отсутствие проекта.

    9. Возможный NullReferenceException при отсутствии ставок

    Фрагмент:
    employee.Rates.FirstOrDefault().Value

    Если список ставок пустой, FirstOrDefault() вернёт null.

    Чем грозит: отчёт завершится HTTP 500.

    Как исправить: проверять наличие подходящей ставки перед расчётом стоимости.

    10. Фильтрация по месяцу выполняется в C#

    Фрагмент:
    .Where(e => e.Date.Year == request.Year &&
    e.Date.Month == request.Month)

    Фильтр применяется после загрузки записей из MongoDB.

    Чем грозит: база не может эффективно отфильтровать данные до передачи их приложению. Это особенно критично при большом количестве записей.

    Как исправить: сформировать начало и конец месяца и выполнить фильтрацию по диапазону дат непосредственно в MongoDB.

1.2. TimeEntriesPage.tsx

Критические:
    1. useEffect без массива зависимостей

    Фрагмент:
    useEffect(() => {
    load();
    });

    Effect выполняется после каждого рендера компонента. load() изменяет состояние через setLoading и setEntries, что вызывает новый рендер.

    Чем грозит: компонент может постоянно отправлять запросы к API и создавать бесконечный цикл обновлений.

    Как исправить: передать зависимости:
    useEffect(() => {
    load();
    }, [props.year, props.month]);

    2. Прямая мутация состояния entries

    Фрагмент:
    entries.push(body);
    setEntries(entries);

    Массив состояния изменяется напрямую, после чего в setEntries передаётся тот же объект массива.

    Чем грозит: React может не определить изменение состояния по ссылке, из-за чего интерфейс не обновится ожидаемым образом.

    Как исправить: создавать новый массив:
    setEntries([...entries, body]);

    3. После сохранения в состояние добавляется не результат сервера

    Фрагмент:
    entries.push(body);

    В состояние добавляется объект, отправленный на сервер, а не созданная сервером запись.

    Чем грозит: в объекте могут отсутствовать серверные поля, например id, amount, employeeName, projectName. После этого UI может работать с неполными данными и завершиться ошибкой на entry.amount.toFixed(2).

    Как исправить: использовать объект, возвращённый API, либо после успешного сохранения повторно загрузить список.

Высокий приоритет

    4. Отсутствует обработка HTTP-ошибок

    Фрагмент:
    const response = await fetch(...);
    const data = await response.json();

    Проверка response.ok отсутствует.

    Чем грозит: ответы 400, 409 и 500 не обрабатываются как ошибки. Пользователь не получает информацию о причине отказа операции.

    Как исправить: проверять HTTP-статус и отображать сообщение об ошибке в интерфейсе.

    5. loading не сбрасывается при ошибке

    Фрагмент:
    setLoading(true);
    ...
    setLoading(false);

    Если запрос завершится исключением, выполнение до setLoading(false) не дойдёт.

    Чем грозит: интерфейс может навсегда остаться в состоянии загрузки.

    Как исправить: использовать try/finally.

    6. Использование any[] для данных

    Фрагменты:
    useState<any[]>([])

    Данные сотрудников и записей не имеют TypeScript-типов.

    Чем грозит: компилятор не проверяет существование и типы полей id, amount, employeeName, projectName и других свойств.

    Как исправить: определить интерфейсы для данных API и использовать их в состоянии.

    7. Нестабильные key для элементов списка

    Фрагменты:
    key={index}

    Индекс массива используется как идентификатор элемента.

    Чем грозит: после добавления или удаления элементов React может некорректно переиспользовать элементы DOM.

    Как исправить: использовать стабильный идентификатор записи:
    key={entry.id}

    8. Дата отправляется в локализованном формате

    Фрагмент:
    new Date(date).toLocaleDateString()

    Формат зависит от локали пользователя.

    Чем грозит: один и тот же код может отправлять даты в разных форматах, что создаёт проблемы при обработке на сервере.

    Как исправить: использовать однозначный формат даты, например ISO 8601.

Средний приоритет

    9. Итоги рассчитываются только на клиенте

    Фрагмент:
    for (let i = 0; i < filtered.length; i++) {
    total = total + parseFloat(filtered[i].amount);
    }

    Итог рассчитывается по массиву, загруженному в компонент.

    Чем грозит: при использовании серверной пагинации итог может быть рассчитан только по текущей странице, а не по всему отфильтрованному списку.

    Как исправить: получать агрегированные итоги с сервера либо использовать отдельный запрос для расчёта итогов.

    10. Не обрабатываются ошибки удаления

    Фрагмент:
    await fetch("/api/time-entries/" + id, {
    method: "DELETE"
    });

    load();

    Результат DELETE не проверяется.

    Чем грозит: при неудачном удалении пользователь не узнает об ошибке, а приложение просто повторно загрузит данные.

    Как исправить: проверять response.ok и отображать ошибку пользователю.

2. Структурные изменения
    Разделил бы работу с MongoDB и бизнес-логику. Сейчас TimesheetReportHandler одновременно выполняет запросы к MongoDB, выбирает ставку, рассчитывает стоимость, группирует записи и формирует результат отчёта. Я бы вынес работу с данными и расчётные операции в отдельные компоненты/сервисы. Handler должен координировать выполнение запроса, а не содержать всю логику самостоятельно.

    Перенёс бы формирование отчёта в MongoDB aggregation pipeline. Вместо загрузки записей в память использовал бы последовательность $match → получение данных сотрудников/проектов → выбор ставки → расчёт стоимости → $group. Это позволит обрабатывать большой объём данных непосредственно на стороне базы.

    Вынес бы типы данных API на фронтенде. Вместо any[] определил бы интерфейсы для TimeEntry, Employee и DTO ответов API. Это позволит TypeScript контролировать соответствие данных, которые использует компонент, фактическому контракту API.

    Вынес бы работу с API из компонента React. TimeEntriesPage сейчас одновременно отвечает за отображение, состояние формы, HTTP-запросы, обработку данных и расчёт итогов. Я бы вынес API-вызовы в отдельный слой, а компонент оставил ответственным преимущественно за UI и управление состоянием.

    Сделал бы единый механизм обработки ошибок API. Ошибки 400/409 должны преобразовываться в понятные сообщения для пользователя. Компонентам не пришлось бы самостоятельно разбирать HTTP-ответы и исключения.

    Для списка записей использовал бы серверную пагинацию и фильтрацию. При больших объёмах данных компонент не должен загружать и обрабатывать весь список целиком. Фильтры, пагинация и получение данных должны выполняться на стороне API/БД.
